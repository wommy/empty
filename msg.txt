endpoint: the etab fuzz precondition admits only options putexportent writes

Nightly run 41037354967 (job 124001380053) failed FuzzNFSEtabParse on the
etab "0\t(0)\n/tank/v/a\t10.0.0.0/24(ro)\n": the verifier said 10.0.0.0/24
is served ro while mountd's model gives it no export.

Both sides are right for etab as written. LoadEtab (internal/nfsref/
exportfs.go:459) stops at the first getexportent failure, and parseopts
(internal/nfsref/exports.go:470) fails on the unknown option "0", so the
valid second line is never loaded. ParseEtab keeps reading and keeps that
line. This input could not have been written by putexportent, so the
precondition was wrong to admit it: etabLineRE accepted any token inside
the parentheses.

optionsAsWritten now checks the option list against the grammar
nfsref.PutExportent prints: bare flags, and valued options in the forms it
prints them (fsid=N or a 32-hex-digit UUID, fsid before reexport and
reexport once, reexport=auto-fsidnum|predefined-fsidnum, mountpoint[=path],
refer=/replicas=, squash_uids=/squash_gids= ID lists, anonuid=N,
anongid=N, sec=flavor(:flavor), xprtsec=mode(:mode)). The writer never
prints "0", "anonuid=x", "fsid=x", "sec=bogus", "ro=1", an empty item, or
a trailing comma. TestEtabAsWrittenAcceptsPutExportent pins that every
line PutExportent prints is admitted.

Not changed, on purpose:
- the host and path rules: the parser maps an empty host to "*", and a
  relative path is skipped without stopping the file, so neither causes
  this divergence;
- two lines PutExportent prints that LoadEtab still rejects, with the
  file's next export lost (probed with LoadEtab):
    /x\t*(squash_uids=1-3,5,anonuid=0,anongid=0,sec=sys,...)
    /x\t*(squash_gids=anonuid=0,anongid=0,sec=sys,...)
  The first has a multi-element ID list; the model's parsesquash stops at
  the first range (its comment cites exports.c:655-662, 874-904) and reads
  "5" as an unknown option. The second is the empty squash_gids list that
  runs into anonuid=. Both are admitted, because the writer prints them.
  If the nightly fuzz finds either, the question is whether real mountd
  accepts it, which needs the nfs-utils source.

Source: the nfs-utils source was NOT fetched in this session (raw GitHub
returned 404 for the repo path, github.com and the API returned 403, and
add_repo could not find nfs-utils/nfs-utils). The line numbers above are
the repo's own citations in nfsref, not lines read from upstream.

The reproducer 8dbaba9de1f231eb was rebuilt from its hash: a search of
about 131k etab/data candidates found this one (etab without the final
newline, data "02") as the only match for that prefix. The serializer
reproduced both existing corpus hashes. The file fails at HEAD with the
logged message and passes after this change.
