# Operator-experience audit: can an operator see a production failure and act on it?

Scope: HEAD 040e38b, read-only. Sources: `cmd/zfs-endpoint/{main,startup,reconcile,lockparent}.go`, `cmd/zfs-csi/main.go`, `internal/server/{daemon,server}.go`, `internal/zfs/{audit,runner,zfs,errors}.go`, `internal/endpoint/{errors,apply,endpoint,plan,headroom,reconcile,table}.go`, `internal/csi/identity.go`, `deploy/systemd/*`, `deploy/k8s/controller.yaml`, README, ADR 0006.

## What the operator has today (baseline)

**zfs-endpoint (journald, JSON from slog, `journalctl -u 'zfs-endpoint@*' -o cat`):**
- One `"msg":"rpc"` line per non-health call (`daemon.go:181-199`), logged after the handler returns. Fields: `method`, `code`, `duration` (ns), `peer`, `role`, `peer_uid/gid/pid`, `error` (on failure), and `request_id`. **It is always `level=INFO`**, even for INTERNAL. It has **no volume id or name field**. Only DeleteVolume and DeleteSnapshot log the id first, in a separate `"delete volume"`/`"delete snapshot"` line (`server.go:166,214`).
- Mutating zfs commands only (`audit.go`): `"zfs exec"` (INFO, `argv`) before the command runs, then `"zfs done"` (INFO, `argv`, `duration`) or `"zfs failed"` (**WARN**, `argv`, `duration`, `error`). **Reads (`get`, `list`, the scan) are never logged.**
- Health: `"health: not serving"` (WARN, `error`) and `"health: serving"` (INFO), logged only when the state changes. Every 30 s the probe runs `zfs get type <parent>` (10 s timeout) and re-checks crossmnt exposure, which logs `"health: parent is under a crossmnt NFS export..."` (WARN, `parent`, `mountpoint`, `exports`) once each time the exports change.
- Lifecycle: `"openzfs"`, `"waiting for the parent dataset"` (WARN, `retry_in`, `error`), `"serving"`, `"shutting down"`, `"drain timed out: cancelling in-flight calls"` (WARN, `in_flight`), `"handlers still running after stop: exiting anyway"` (ERROR), `"handler panic"` (ERROR, `stack`).
- Fatal: **one plain-text, non-JSON line**, `zfs-endpoint: <err>`, then exit 78/75/1 (`main.go:41-43`).
- Metrics: none. ADR 0006 says the journal is the metrics source, but nothing emits a gauge or a periodic stats line. Every count has to be derived from the `rpc` lines.

**zfs-csi (`kubectl logs -c zfs-csi`):** logs `serving` and `shutting down`, and nothing per call. It never calls `slog.SetDefault`, so it writes **Go's default text format** (`2026/10/27 10:00:00 INFO serving csi=...`), not JSON. ADR 0006 ("Both log structured JSON") is wrong about this. It forwards no `x-request-id` and drops the `csi.storage.k8s.io/pvc/*` parameters, so the endpoint never learns which PVC made a call. Endpoint codes and messages reach PVC/PV events verbatim (`rpc error: code = X desc = ...`).

**Correlation:** volume id = PV name (`pvc-<uid>`) = dataset `<parent>/pvc-<uid>`, so `journalctl -u zfs-endpoint@... -o cat | grep pvc-<uid>` finds the zfs argv and most error texts. That grep is the main tool, and it works because ids appear in messages, not because of a field.

**Reconcile timer:** a dry run that writes plain text to the reconcile unit's journal (`plan_digest:`, `actions planned (dry run, nothing changed): N`, `  destroy <id>: <reason>`, `skipped: N`, `  <id>: <reason>`). **It exits 0 whatever it finds.** It fails only when the call fails (for example when the endpoint is down).

**README runbooks:** only "Runbook: Reconcile". Nothing covers startup exits, NFS, capacity, lock contention, hung zfs, or foreign datasets. Some of this is in the unit-file comments (exit 78, journald rate limit).

## Scenario walk-throughs

### 1. Create failed after a change and was left uncommitted (leaked row, pinned clone source)
- **At failure:** `zfs failed` WARN (argv of the op that failed), then `rpc` INFO `code=Aborted error="op 3/5 set tank/k8s/vols/pvc-x (earlier ops applied; a retry converges): zfs set ...: <kind>: <stderr>"`. An unclassified failure on the plan's first op stays `Internal`. The PVC event is `ProvisioningFailed ... code = Aborted desc = op 3/5 ...`. The provisioner retries, and a successful retry resumes from the marker.
- **If the PVC is deleted first:** the row stays as `<parent>/pvc-x` with no `provision_success`. Nothing is logged about it again. The daily report lists `destroy pvc-x: uncommitted: provision never completed` once it is older than `-min-age` (1h); before that it shows `pvc-x: younger than the minimum age`. **The timer never applies**, exits 0, and nobody is notified. An uncommitted NFS create keeps its `sharenfs`, so **it stays exported to its clients until someone applies a Reconcile**. The report does not say so.
- **Pinned clone source:** a clone-from-volume that made the clone and then failed leaves an uncommitted clone. The source PV's DeleteVolume then returns `FAILED_PRECONDITION volume pvc-src has dependent clone pvc-x` (`plan.go:823`). The PV stays `Released` with repeating `VolumeFailedDelete` events. **The message does not say pvc-x is an abandoned, uncommitted create, or that Reconcile -apply clears it.** If the snapshot was cut but the clone never made, the stamped snapshot is collected with the source's delete or reported as `clone-source snapshot without a clone`, so that case is fine.
- **Visible without code?** Partly. **Greppable?** Yes: `uncommitted: provision never completed`, `earlier ops applied`. **Runbook?** Reconcile runbook step 1 mentions abandoned creates, but no runbook covers "source PV will not delete".

### 2. NFS export served beyond its list / exposure refused
- **Startup:** a parent under a crossmnt export exits **78** with `zfs-endpoint: parent X (mounted at M) is under a crossmnt NFS export ...; unshare it ... and start again`. That is clear.
- **Runtime, parent becomes exposed:** one WARN, `health: parent is under a crossmnt NFS export, which serves every volume to its clients; unshare it ...`, logged once on change. Health stays SERVING, by design. Nothing repeats it, so it is easy to miss.
- **Create in NFS mode:** `FAILED_PRECONDITION volume pvc-x is served beyond its export by the NFS export table: <lines>; remove these exports ...; the volume is not committed`. An exportfs miss gives `UNAVAILABLE sharenfs on ... is set, but the NFS export table does not serve ...; check exportfs and the NFS server ...; the volume is not committed`. A stopped nfsd gives `UNAVAILABLE the NFS server is not running on the storage host (no nfsd threads)...`. These arrive as PVC events verbatim, and they are good.
- **Publish (admin socket):** `FAILED_PRECONDITION volume X is served beyond its client list ...`, refused with no change made.
- **Gaps:** the uncommitted, still-exported row (see 1). The Reconcile report never shows exposure ("reporting unrecorded exports" is still listed as open). No runbook.

### 3. Pool nearly full
- **`-min-free-bytes` (default 0, off):** `RESOURCE_EXHAUSTED create volume pvc-x: a new child of the parent gets N bytes and this reserves M, which would leave less than the F-byte floor (-min-free-bytes)`, appearing as a PVC event and in the `rpc` line at INFO. It is greppable as `-min-free-bytes`.
- **ENOSPC from zfs:** `zfs failed` WARN `error="zfs create ...: no space: ... out of space"`. If it comes before any change, the code is `RESOURCE_EXHAUSTED` (final for the provisioner under Immediate binding). If it comes after a change, the code is `ABORTED ... (earlier ops applied; a retry converges)`, and **the provisioner retries forever while the message keeps promising convergence**. That is the right code, but misleading text while the pool stays full.
- **No early warning:** health does not read space, nothing logs "below floor", CSIStorageCapacity is off (`rbac.yaml`: no `--enable-capacity`), and snapshots are not guarded. The first sign is a failed create.
- **Runbook:** none. The README's "Errors" section explains the codes, but it is a design section, not a runbook.

### 4. Endpoint down or restarting
- **systemd:** `Restart=on-failure`, 2 s up to 60 s backoff, `StartLimitIntervalSec=0`, so it restarts forever. `systemctl status` shows `status=75/TEMPFAIL` or `1/FAILURE`, and `NRestarts` climbs. A pool that never comes back shows as a WARN `waiting for the parent dataset` loop followed by exit 75, repeating forever with nothing escalated.
- **While draining:** calls get `UNAVAILABLE endpoint is shutting down`, health goes NOT_SERVING, and there are WARN lines if the drain times out.
- **zfs-csi side:** calls fail `UNAVAILABLE ... dial unix /run/zfs-endpoint/sock/<p>/endpoint.sock: connect: no such file or directory` (or `connection refused`). They pass through to PVC events and the sidecars retry. The 5 s reconnect cap means recovery is fast. **zfs-csi logs nothing.**
- **Probe ready=false:** only the sidecars call Probe, and only at startup (ProbeForever). The controller pod has **no livenessprobe container**, so a runtime NOT_SERVING (suspended pool, slots exhausted) is invisible from Kubernetes. Calls are not refused by NOT_SERVING either. It appears only in the endpoint journal as `health: not serving`.
- **Pod scheduled while the endpoint has never run:** the `hostPath type: Directory` mount fails and the pod sits in ContainerCreating with a `FailedMount` event. The cause is clear enough.
- **Reconcile timer:** the unit fails (`zfs-endpoint: reconcile on ...: rpc error: code = Unavailable ...`, exit 1). Good.

### 5. Dataset replaced or foreign under the parent
- **Mid-apply replacement:** `ABORTED <ds> is not the dataset the plan inspected (guid A, now B): it was replaced since; retry` (`apply.go:118`). The retry re-plans and then hits the ownership refusals below.
- **Ownership refusals:** DeleteVolume gives `FAILED_PRECONDITION dataset tank/k8s/vols/pvc-x is not managed`. **It does not say why:** no local marker, a `received` marker, or `csi_volume_name` mismatch (a rename). Create gives `ALREADY_EXISTS dataset X exists and is not the endpoint's volume X (managed=false, volume name "...")`, which is better. Get, List, and Expand treat the dataset as absent (NOT_FOUND), so a PV whose dataset was swapped looks like a missing volume.
- **Reconcile:** `PlanReconcile` drops unowned rows silently (`if !r.OwnedVolume() ... continue`). **A foreign or received dataset sitting at a PV's name never appears in any report.**
- **Runbook:** none. ADR 0003 explains the rule but not the remedy (`zfs inherit`, or set the marker locally, or rename it away).

### 6. Reconcile wants to delete more than `-max-deletions`
- The dry run prints the whole plan with no undesired count and no comparison against the cap. The README tells the operator to count `not in the desired set` lines by hand.
- On apply: `zfs-endpoint: reconcile on <sock>: rpc error: code = FailedPrecondition desc = would collect N volumes not in the desired set, more than max deletions 10: check the desired set with a dry run, then raise max deletions`, exit 1. The server returns only the error, so the plan is discarded. The endpoint logs `reconcile` INFO (`desired`, `min_age_seconds`, `dry_run`) and an `rpc` `code=FailedPrecondition` line.
- The README covers this well (step 2). It is visible and greppable (`more than max deletions`). Low risk, and the daily timer never reaches it because its desired set is empty.

### 7. Lock contention (ABORTED after `-lock-wait`)
- `rpc` INFO `code=Aborted error="operation pending on [pvc-x]"` (`endpoint.go:469,475`), and the PVC event is the same. The provisioner retries with backoff. **The message does not give the wait time, the holder (method or request_id), or how long the lock has been held**, and nothing logs at the moment the lock wait begins.
- Reconcile reports `pvc-x: busy: another operation holds it; next reconcile`.
- To find the holder, the operator must spot a `zfs exec` for that dataset with no `zfs done`. That works only if the holder is mutating: a holder stuck in a scan leaves no line at all. Unhelpful in practice.
- **Runbook:** none. The README Design section explains the lock-wait semantics.

### 8. zfs CLI hangs
- **There is no per-command timeout.** A command is bounded only by its context: the sidecar's `--timeout=60s`, `DefaultCallTimeout` (10 min) for callers that set no deadline, 10 s for the health and startup probes, and 5 min for the reconcile CLI. On expiry the runner sends SIGTERM to the process group, waits `WaitDelay` (5 s), then SIGKILL. The result is `DEADLINE_EXCEEDED` (or `ABORTED` on cancel), whose error ends with `interrupted, outcome unknown: ... context deadline exceeded`. That is good, and greppable as `outcome unknown`.
- **A zfs in D state (suspended pool) cannot be killed:** the handler, its `-max-zfs` slot, and its volume lock stay held. Because the `rpc` line is logged only after the handler returns, **a stuck call leaves no `rpc` line**. A stuck mutating command leaves an unmatched `zfs exec`; a stuck read leaves nothing. Once all 8 slots are held, callers fail `DEADLINE_EXCEEDED ... waiting for a free zfs slot`, the health probe fails the same way, and the endpoint logs WARN `health: not serving error="... waiting for a free zfs slot ..."`. That message is the only clear signal, and only the endpoint journal shows it (see 4).
- **Shutdown:** WARN `drain timed out ... in_flight=N`, then ERROR `handlers still running after stop: exiting anyway`.
- No slow-command line and no in-flight or slot gauge. No runbook covers `zpool status` / `failmode`.

### 9. Startup refusals
- **Exit 78** (`RestartPreventExitStatus=78`, no restart): bad flags; invalid or over-long `-parent`; a socket path that is too long or inside the lock directory; `-admin-listen` under the CSI socket directory; an unknown `-socket-group`; not root without `-allow-non-root`; `-nfs-server` without root; another endpoint holding this parent, an ancestor, or a descendant (`another endpoint already manages X ... (lock P)`); a lock that is a symlink; zfs missing (`cannot run zfs`); OpenZFS other than 2.4 (`... (ADR 0004)`); a parent that is not a filesystem; crossmnt exposure; legacy-prefix-only volumes (`N datasets under P carry democratic-csi:managed_resource ... pass -property-prefix democratic-csi ...`).
- **Exit 75:** `cannot read the OpenZFS version` (module not loaded), `parent dataset P is not available after 60s`, or a failed legacy-prefix scan. Restarted forever.
- **Exit 1:** `serve: ...`, and lock errors other than EWOULDBLOCK.
- **Exit 0:** SIGTERM during startup (`stopped during startup`, INFO).
- **What the operator sees:** `systemctl status` shows `code=exited, status=78/CONFIG`, and the last journal line is the plain-text `zfs-endpoint: <message>`. The messages are specific and say what to do. **The fatal line is not JSON**, so a JSON pipeline (`-o json` parsing `MESSAGE` as JSON) drops it or treats it as garbage. It carries no `exit_code` field, and there is no README table of exit codes; only the unit comments and `startup.go` list them.

**Cheapest high-value set:** #1 (summary line plus `-fail-on-findings`), #2 (rpc level and `volume_id`), #3a (`zfs slow`) and #6 (zfs-csi JSON plus request id). Each is a few lines and needs no new dependency. Together they would make ADR 0006's "journald is the metrics" true: `journalctl -p warning -u 'zfs-endpoint*'` would show every failure, every slow zfs command and every report with findings.

**One README section** would cover the rest: "Runbook: when a PVC is stuck", with one paragraph per code and message family: `Aborted operation pending`, `DeadlineExceeded outcome unknown` / `waiting for a free zfs slot`, `ResourceExhausted` / `no space`, `FailedPrecondition has dependent clone` / `not managed` / `served beyond`, `Unavailable connect` / `NFS export table does not serve` / `no nfsd threads`, and startup exits 75/78.
