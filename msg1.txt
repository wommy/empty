endpoint: report a filesystem's mountpoint with symlinks resolved, so share is the exported path

Publish and the create-time export check verify the export in etab at
realPath(mountpoint), as nfsd_realpath records it, but volumeView handed
back zfs's mountpoint unresolved, and zfs-csi passes that on as
volume_context share. With a parent mounted below a symlink, an NFSv4
client walks share through nfsd's pseudo-root, which holds only resolved
paths, and the mount fails (deploy seam review D3).

The endpoint now reports Mountpoint resolved (realPath, a no-op when the
path does not resolve, e.g. unmounted), so share, the mountpoint key and
the etab entry agree. The fix sits in the endpoint because zfs-csi runs
in a pod and cannot resolve host paths. The proto comment is unchanged
(gen/ would drift); the Go Volume field and CtxShare document it.

TestNFS_ShareIsTheResolvedPath: a parent mountpoint under a symlink on
the simulator; share is EvalSymlinks(mountpoint), etab serves it, and a
repeat and ListVolumes agree. It fails without the change. It sets no
nfs.uid/gid/mode: SetRoot refuses any symlink on the path
(RESOLVE_NO_SYMLINKS), so a symlinked parent with root parameters still
fails CreateVolume FailedPrecondition. PublishFileExport's export_path
is left unresolved (TestFileExportResolvesSymlinks pins it;
zfs-csi does not use it).
